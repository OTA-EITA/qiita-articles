2025 年 1 月に書いた記事です。2026 年 10 月に、公式ドキュメントで内容を確かめ直して更新しました。

WSL2 を使い続けていると、タスクマネージャーの **Vmmem**（WSL2 の仮想マシンのプロセス）のメモリ使用量が増え続け、Windows 側のメモリが足りなくなることがあります。

結論から書くと、いちばん確実なのは `%USERPROFILE%\.wslconfig` の `memory` で WSL2 に渡すメモリの上限を決めることです。そのうえで、キャッシュの自動回収（`autoMemoryReclaim`）や `wsl --shutdown` を補助として使います。

WSL2 で Docker や VS Code を動かしていて、Windows が重くなって困っている人向けです。

内容は Microsoft Learn の [Advanced settings configuration in WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)（2026 年 10 月 16 日更新版）で確かめています。既定値は WSL のバージョンで変わってきたので、手元の WSL のバージョンを `wsl --version` で確認してから読んでください。

## なぜメモリが増え続けるのか

主な原因は、**Linux のファイルキャッシュと、WSL2 の仮想マシンのメモリの扱い**の組み合わせです。

### 1. Linux はファイルキャッシュをすぐには手放さない
Linux は、読み書きしたファイルの内容をメモリにキャッシュします。このキャッシュは、基本的にメモリが足りなくなるまで残ります。そのため、ビルドや `git` 操作、Docker のイメージ操作など、大量のファイルを扱うとキャッシュが膨らみます。

### 2. WSL2 の VM は増えたメモリをすぐには Windows に返さない
WSL2 は仮想マシン（VM）の上で Linux を動かしています。VM のメモリは Linux の使用量に応じて増えます。Linux から見るとキャッシュは「使っているメモリ」なので、キャッシュが膨らむと Vmmem も大きいままになります。

## やること 1: .wslconfig でメモリの上限を決める（おすすめ）

WSL2 に渡すメモリの上限を決めておけば、Windows 側が使い切られることはなくなります。

### 設定手順
1. `%USERPROFILE%\.wslconfig`（例: `C:\Users\YourName\.wslconfig`）を作成または編集する
2. 以下の内容を書く

   ```ini
   [wsl2]
   memory=6GB
   swap=6GB
   ```

3. PowerShell で `wsl --shutdown` を実行し、ディストリビューションを起動し直す

公式ドキュメントでは、設定を変えたあとは WSL の VM が完全に止まるのを待つ必要があり、ふつうは全部のシェルを閉じてから 8 秒ほどかかると書かれています（「The 8 second rule」）。`wsl --list --running` で、動いているディストリビューションが残っていないか確かめられます。

なお、Windows のスタートメニューにある「WSL Settings」からも同じ設定を変えられます。公式ドキュメントは、`.wslconfig` を直接書くよりこちらを勧めています。

### 設定のポイント
- `memory` の既定値は、現在のドキュメントでは「Windows の総メモリの 50%」です。以前の記事では「50% か 8GB の少ない方」と書いていましたが、いまのドキュメントにはその記述はありません
- `swap` の既定値は「Windows のメモリの 25%（GB 単位で切り上げ）」です。`swap=0` にするとスワップファイルを作りません。メモリが足りなくなったときに逃げ場がなくなるので、上限を小さくするときは 0 にしない方が安全です
- `memory=6GB` の値は、PC のメモリと WSL2 の使い方に合わせて変えてください

私は `memory` を 6GB ぐらいにして、足りない分はスワップで補っています。いろいろなプロジェクトを同時に進めるには、これぐらいがちょうどよいと感じています。スワップが使われると少し重くなりますが、Windows ごと固まるよりはましです。

## やること 2: キャッシュの自動回収を確かめる（autoMemoryReclaim）

以前の記事では「WSL2 にはメモリを返す管理機能はない」と書きましたが、これは正しくありませんでした。2023 年 9 月のアップデートで `autoMemoryReclaim` という設定が入っています（[Windows Subsystem for Linux September 2023 update](https://devblogs.microsoft.com/commandline/windows-subsystem-for-linux-september-2023-update/)）。

`.wslconfig` の `[experimental]` セクションに書きます。

```ini
[experimental]
autoMemoryReclaim=gradual
```

公式ドキュメントでの値の意味は次のとおりです。

| 値 | 動き |
|---|---|
| `disabled` | 自動回収をしない |
| `gradual` | キャッシュを少しずつ自動で回収する |
| `dropCache` | キャッシュをすぐに回収する |

現在のドキュメントでは、既定値は `dropCache` と書かれています。お使いの WSL のバージョンで既定がどうなっているかは、私は確かめていません。明示したいときは上のように書いてください。

注意点として、2023 年 9 月の発表記事には、`gradual` は cgroups v1 を無効にするので、WSL の中でサービスとして動かしている Docker デーモンが動かなくなる、と書かれています。Docker を WSL の中で直接動かしている人は気をつけてください。

ほかに、ディスク側の話ですが、`[experimental]` の `sparseVhd=true` にすると新しく作る仮想ディスクが自動で縮むようになります。

## やること 3: キャッシュを手動で捨てる

上限を決めない場合は、キャッシュを手動で捨てる方法もあります。

```sh
sudo sh -c "sync && echo 3 > /proc/sys/vm/drop_caches"
```

スワップも空にしたいときは、続けて次を実行します。

```sh
sudo swapoff -a && sudo swapon -a
```

### 注意点
- `swapoff -a` は、スワップに出ているページをすべてメモリに読み戻します。**メモリに空きがないと失敗します**。`swapoff(8)` の man ページでも、終了コード 2 は「system has insufficient memory to stop swapping (OOM)」です（[swapoff(8)](https://man7.org/linux/man-pages/man8/swapoff.8.html)）。スワップの使用量が多いと、終わるまでに時間がかかることもあります。メモリが逼迫しているときに実行するのは避けて、`free -h` で空きを見てからにしてください
- `drop_caches` について、Linux カーネルのドキュメントは「キャッシュを作り直すために I/O と CPU を使うので、テストやデバッグ以外での利用は勧めない」としています（[Documentation for /proc/sys/vm/](https://docs.kernel.org/admin-guide/sysctl/vm.html)）。定期的に実行するより、上限の設定や `autoMemoryReclaim` に任せる方が素直です
- 以前の記事では「WSL2 では systemd や cron が動かない」と書きましたが、いまは違います。WSL 0.67.6 以降は `/etc/wsl.conf` に次を書くと systemd が使えます。`wsl --install` で入る現在の Ubuntu では systemd が既定になっています（[Use systemd to manage Linux services with WSL](https://learn.microsoft.com/en-us/windows/wsl/systemd)）。systemd が動けば cron や systemd のタイマーも使えます

```ini
[boot]
systemd=true
```

## やること 4: WSL2 を止める

WSL2 の VM を止めると、キャッシュも含めてメモリが Windows に返ります。いちばん手軽です。

```sh
wsl --shutdown
wsl
```

`wsl --shutdown` は動いているすべてのディストリビューションを止めます。1 つだけ止めたいときは `wsl --terminate <ディストリビューション名>` を使います。

## 起きやすい使い方

次のような使い方では、メモリが増えやすいです。

- **Visual Studio Code の Remote - WSL を使う**
- **Docker Desktop（WSL2 バックエンド）を使う**
- **大きなコードベースで開発する**
- **機械学習やデータ解析など、メモリを多く使う作業をする**

これらを**組み合わせている環境ほど**、先に上限を決めておく価値があります。

## やること（チェックリスト）

- [ ] `%USERPROFILE%\.wslconfig` の `[wsl2]` に `memory` を書いた（Windows 側に残す分を先に決めて、残りを WSL2 に渡す）
- [ ] `swap` を 0 にしていない
- [ ] `wsl --shutdown` のあと、`wsl --list --running` で止まったのを確かめてから起動し直した
- [ ] `wsl --version` で WSL のバージョンを確かめた
- [ ] 必要なら `[experimental]` の `autoMemoryReclaim` を明示した（WSL の中で Docker デーモンを直接動かしているなら `gradual` は避ける）
- [ ] 定期的にキャッシュを捨てたいなら、`/etc/wsl.conf` で systemd を有効にしてから cron かタイマーを使う

## 確かめていないこと

- `autoMemoryReclaim` の既定値が、手元の WSL のバージョンで実際に `dropCache` になっているか
- Docker Desktop を使っている場合に、Docker Desktop 側の設定と `.wslconfig` のどちらが優先されるか
