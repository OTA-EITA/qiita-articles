## 1. Amazon EMR とは

Amazon EMR（旧称 Elastic MapReduce）は、AWS 上で Hadoop や Spark などのビッグデータ処理のフレームワークを動かすための、マネージドなクラスターのサービスです。

EMR では **Apache Spark** がよく使われます。Spark はクラスター管理の仕組みとして YARN のほかに、Spark 単体のスタンドアロンモードや Kubernetes でも動きます（[Cluster Mode Overview](https://spark.apache.org/docs/latest/cluster-overview.html)）。ただ EMR on EC2 では、**Hadoop の YARN がリソース管理、Spark がデータ処理のエンジン**という組み合わせで動かすのが基本です。データの置き場所は HDFS のほか、EMRFS を通して S3 も使えます。

Hadoop と Spark の関係を表にまとめました。

### Hadoop と Spark の比較表

| 項目 | **Hadoop（MapReduce）** | **Apache Spark** |
|---|---|---|
| **目的** | 分散バッチ処理 | 分散データ処理（バッチとストリーミング） |
| **処理の仕方** | MapReduce によるバッチ処理 | バッチ処理とストリーミング処理 |
| **速さ** | 中間結果をディスクに書くので、繰り返しの多い処理は遅くなりやすい | 中間結果をメモリに置けるので、繰り返しの多い処理で速くなりやすい |
| **データの置き場所** | HDFS | HDFS、S3、Cassandra、HBase、JDBC など |
| **書ける言語** | Java（MapReduce） | Scala、Java、Python、R |
| **ストリーミング** | 不向き | Structured Streaming（以前は Spark Streaming） |
| **機械学習** | Mahout など | MLlib |
| **API** | Map と Reduce を書く | RDD、DataFrame、Dataset |
| **主な連携先** | Hive、HBase、Pig、Oozie | Hive、HBase、Cassandra、Kafka |
| **障害への強さ** | HDFS のレプリケーション | RDD の再計算（リネージ） |

なお、旧来の Spark Streaming（DStream）は、Spark のドキュメントで「previous generation」「legacy project」とされています。今から書くなら Structured Streaming を使います（[Spark Streaming Programming Guide](https://spark.apache.org/docs/latest/streaming-programming-guide.html)）。

### Hadoop と Spark の関係
- **Spark は Hadoop の代わりというより、組み合わせて使われることが多い**
  - Spark は Hadoop の HDFS をデータの置き場所として使える
  - Spark は Hadoop の YARN をリソース管理に使える
  - MapReduce で書いていた処理を Spark に置き換えると、速くなることが多い
- **MapReduce はバッチ処理向き、Spark はバッチとストリーミングの両方に使える**

### 使い分けの目安
| やりたいこと | 候補 |
|---|---|
| 大規模なバッチ処理（ログ解析、レポート生成） | Hadoop（MapReduce）または Spark |
| 速いデータ処理と、ほぼリアルタイムの分析 | Spark |
| データレイクとしての分散ストレージ | HDFS（EMR では S3 を使うことも多い） |
| 機械学習のモデルの学習 | Spark MLlib |
| ストリーミングデータの処理（IoT、SNS のデータなど） | Spark Structured Streaming |

## 2. なぜ Amazon EMR を触っておくとよいのか

フリーランスとして大型案件の面談を受けると、システム設計の質問で「**大量のデータをどう処理するか**」と聞かれることがよくあります。そのたびに、多くの企業が何らかのビッグデータのツールを入れていると感じました。

データエンジニアリングでは、Python や SQL に加えて、**ビッグデータのフレームワークを扱えること**が求められる場面があります。EMR を一度触っておくと、大規模データの処理や ETL パイプラインの話についていきやすくなると思います。

## 3. Amazon EMR の仕組み

### 3.1. クラスターとノードの種類

EMR は **YARN（Yet Another Resource Negotiator）** でクラスターのリソースを管理します。YARN は、クラスター全体を管理する「ResourceManager」と、各ノードで動く「NodeManager」で構成されています。

EMR のクラスターには、次の 3 種類のノードがあります（[Understand node types in Amazon EMR](https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-master-core-task-nodes.html)）。

1. **プライマリノード（以前の呼び方はマスターノード）**
   - クラスターを管理する。YARN の ResourceManager や HDFS の NameNode が動く
   - ジョブの状態やインスタンスグループの状態を監視する

2. **コアノード**
   - HDFS の DataNode として、データを保存する
   - YARN の NodeManager として、Spark の executor などの計算も行う

3. **タスクノード（任意）**
   - コアノードと同じように計算を行うが、HDFS の DataNode は動かず、HDFS にデータを保存しない

### 3.2. ほかの AWS サービスとの連携

- **Amazon S3**: データの置き場所として使う。EMRFS（EMR File System）を通して S3 を読み書きできる
- **Amazon EC2**: クラスターの各ノードは EC2 インスタンスとして起動する
- **Amazon VPC**: クラスターを置くネットワーク

## 4. スケーリング

EMR のクラスターは、手動でノードを増減できるほか、**EMR マネージドスケーリング**を使うと、負荷に応じて自動で増減させられます（[Using managed scaling in Amazon EMR](https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-managed-scaling.html)）。

たとえば、ピーク時にノードを増やし、空いている時間に減らしてコストを抑えられます。この記事のハンズオンでは、スケーリングは手動（台数固定）にしています。

### 5.2. VPC を作る

次の設定で VPC を作成します。

| 項目 | 設定 |
|---|---|
| 作成するリソース | VPC など |
| 名前タグの自動生成 | オン（例: `emr-labor-force-hokkaido`） |
| IPv4 CIDR ブロック | 10.0.0.0/16 |
| IPv6 CIDR ブロック | なし |
| テナンシー | デフォルト |
| アベイラビリティーゾーンの数 | 2 |
| パブリックサブネットの数 | 2 |
| プライベートサブネットの数 | 0 |
| NAT ゲートウェイ | なし |
| VPC エンドポイント | S3 ゲートウェイ |

NAT ゲートウェイは時間単位で課金されるので、「なし」にしています。S3 のゲートウェイエンドポイントには、時間単位の料金もデータ処理の料金もかかりません（[Amazon VPC pricing](https://aws.amazon.com/vpc/pricing/)）。

### 6.2. スクリプトを用意する

EMR では、クラスターで実行する処理の単位を「ステップ」と呼びます。ステップを使うと、クラスター上でデータ処理を自動で実行できます。

ここでは、次のステップを作ります。

**CSV を ETL 処理する** → **Parquet 形式で S3 に保存する**

スクリプトは、引数で受け取った CSV を読み込みます。日本のオープンデータによくある説明用の行を消し、日本語の列名を英語に変えてから、振興局ごとに集計します。最後に、引数で指定した S3 の場所に Parquet 形式で保存します。CSV は Shift_JIS なので、読み込むときに `encoding` を指定しています。

```main.py
from pyspark.sql import SparkSession
from pyspark.sql.functions import col
import argparse


def transform_data(data_source: str, output_uri: str) -> None:
    """
    Transforms inspection data from a CSV file, removes unwanted rows,
    sets the 3rd row as column names, filters out entries containing '計',
    and saves the results as Parquet.

    Args:
        data_source (str): The S3 URI or local path to the input CSV file.
        output_uri (str): The S3 URI or local path where the transformed data should be saved.
    """
    # Initialize Spark session
    with SparkSession.builder.appName("EMR Application").getOrCreate() as spark:
        # Load CSV file into a DataFrame (without using first row as header)
        df = (
            spark.read.option("header", False)  # Don't use first row as header
            .option("encoding", "shift_jis")
            .csv(data_source)
        )
        print("CSV file loaded.")

        # Assign an index to each row
        indexed_rdd = df.rdd.zipWithIndex()

        # Extract the 3rd row (index 2) as column names
        header_row = (
            indexed_rdd.filter(lambda row: row[1] == 2)
            .map(lambda row: row[0])
            .collect()[0]
        )
        print(f"New header extracted: {header_row}")

        # Remove the first six rows except for the 3rd (index 2)
        rows_to_remove = {0, 1, 3, 4, 5}
        filtered_rdd = indexed_rdd.filter(lambda row: row[1] not in rows_to_remove).map(
            lambda row: row[0]
        )

        # Convert back to DataFrame using new column names
        df = spark.createDataFrame(filtered_rdd, schema=header_row)
        print("Header applied and selected rows removed successfully.")

        # Remove rows containing "計" in the 市町村 (City or Town) column
        df = df.filter((col("市町村").isNotNull()) & (~col("市町村").contains("計")))
        print("Rows containing '計' removed successfully.")

        # Rename columns
        df = df.select(
            col("振興局").alias("county"),
            col("コード").alias("location_code"),
            col("市町村").alias("city_or_town"),
            col("区").alias("ward"),
            col("Ａ〜Ｒ全産業（Ｓ公務を除く）_事業所数").alias(
                "workplaces_in_all_industries"
            ),
            col("Ａ〜Ｒ全産業（Ｓ公務を除く）_従業者数").alias(
                "workers_in_all_industries"
            ),
            col("Ａ〜Ｒ全産業（Ｓ公務を除く）_従業者数_男(人)").alias(
                "male_workers_in_all_industries"
            ),
            col("Ａ〜Ｒ全産業（Ｓ公務を除く）_従業者数_女(人)").alias(
                "female_workers_in_all_industries"
            ),
            col("Ａ〜Ｂ農林漁業_事業所数").alias("workplaces_in_primary_industry"),
            col("Ａ〜Ｂ農林漁業_従業者数").alias("workers_in_primary_industry"),
            col("Ａ〜Ｂ農林漁業_従業者数_男(人)").alias(
                "male_workers_in_primary_industry"
            ),
            col("Ａ〜Ｂ農林漁業_従業者数_女(人)").alias(
                "female_workers_in_primary_industry"
            ),
        )

        # Register temporary SQL table
        df.createOrReplaceTempView("labor_force_in_Hokkaido")

        # SQL query to preview data
        transformed_df = spark.sql("""
            SELECT county, 
                SUM(workplaces_in_all_industries) AS total_workplaces, 
                SUM(workers_in_all_industries) AS total_workers, 
                SUM(male_workers_in_all_industries) AS total_male_workers, 
                SUM(female_workers_in_all_industries) AS total_female_workers, 
                SUM(workplaces_in_primary_industry) AS total_workplaces_primary_industries, 
                SUM(workers_in_primary_industry) AS total_workers_primary_industry
            FROM labor_force_in_Hokkaido
            GROUP BY county
        """)

        transformed_df.show(truncate=False)

        # Log the number of rows
        row_count = transformed_df.count()
        print(f"Number of rows in transformed data: {row_count}")

        # Save results in Parquet format
        transformed_df.write.mode("overwrite").parquet(output_uri)
        print(f"Data written to {output_uri}.")


if __name__ == "__main__":
    """
    Parses command-line arguments and executes the transform_data function.
    """
    parser = argparse.ArgumentParser(description="Transform inspection data.")
    parser.add_argument(
        "--data_source", required=True, help="Path to the input CSV file."
    )
    parser.add_argument(
        "--output_uri",
        required=True,
        help="Path to the output directory for Parquet files.",
    )

    args = parser.parse_args()

    # Execute the data transformation process
    transform_data(args.data_source, args.output_uri)
```

## 8. 後片付け（課金を止める）

**ハンズオンが終わったら、すぐにやってください。** 自動終了を設定していても、アイドル時間が過ぎるまではクラスターが動き続けて課金されます。手順は公式チュートリアルの [Step 3: Clean up your Amazon EMR resources](https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-gs.html#emr-getting-started-clean-up) に沿っています。

### 8.1. クラスターを終了する

1. EMR コンソールの「クラスター」で、作ったクラスターを選ぶ
2. 「終了」（Terminate）を押し、確認のダイアログでもう一度「終了」を押す
3. 状態が「終了中（Terminating）」から「終了済み（Terminated）」になるのを待つ。公式チュートリアルでは 5〜10 分かかることがあるとされています

CLI なら次のとおりです。

```sh
aws emr terminate-clusters --cluster-ids <クラスター ID>
aws emr describe-cluster --cluster-id <クラスター ID> --query 'Cluster.Status.State'
```

公式チュートリアルによると、クラスターを終了すると、そのクラスターの EMR の課金と EC2 インスタンスが止まります。終了したクラスターは一覧から消せませんが、メタデータが 2 か月間（無料で）残るだけです。

### 8.2. S3 のオブジェクトとバケットを消す

クラスターを終了してから消します。公式チュートリアルでは、クラスターが動いているとバケットを空にできないことがあるとされています。

バケットにはスクリプト、入力の CSV、出力の Parquet、ログが入っています。コンソールでは、バケットを選んで「空にする」を実行してから「削除」します（[Deleting a general purpose bucket](https://docs.aws.amazon.com/AmazonS3/latest/userguide/delete-bucket.html)）。CLI なら次のとおりです。`--force` はバージョニングされていないオブジェクトを消してからバケットを消します（[aws s3 rb](https://docs.aws.amazon.com/cli/latest/reference/s3/rb.html)）。

```sh
aws s3 rb s3://<バケット名> --force
```

### 8.3. VPC を消す（任意）

使わないなら消しておきます。VPC コンソールで VPC を選んで「VPC を削除」を実行すると、サブネット、ルートテーブル、インターネットゲートウェイ、ゲートウェイエンドポイント、セキュリティグループなども一緒に消えます（[Delete your VPC](https://docs.aws.amazon.com/vpc/latest/userguide/delete-vpc.html)）。EC2 インスタンスが残っていると消せないので、クラスターが「終了済み」になってから実行します。

このほか、EMR のコンソールで作ったサービスロールとインスタンスプロファイル、EC2 キーペアは、ほかで使わないなら IAM と EC2 のコンソールから消して構いません。

### 8.4. 請求を確かめる

- 翌日以降に、Billing and Cost Management の「請求書」や Cost Explorer で、EMR、EC2、S3 の料金が増え続けていないか確かめます（[Analyzing your costs and usage with AWS Cost Explorer](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html)）
- EC2 コンソールで、クラスターのインスタンスが「終了済み」になっているか確かめます
- パブリックサブネットに置いたので、ノードにはパブリック IPv4 アドレスが付いています。パブリック IPv4 アドレスは使用中でも 1 時間ごとに課金されます（[Amazon VPC pricing](https://aws.amazon.com/vpc/pricing/)）。インスタンスが終了していれば止まります
- 心配なら、AWS Budgets で予算のアラートを作っておくと、使いすぎに早く気づけます（[Managing your costs with AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)）

## 9. つまずきやすいところ

### 9.1. ログの見る場所が分かれている

EMR では、Spark や Hadoop のアプリケーションのログ、EMR のシステムのログ、CloudWatch に送るログなど、ログが何か所かに分かれます。ジョブが失敗したときに、どこから見ればよいか迷いやすいです。

まずは、ステップの画面のログファイル（stderr）と、クラスターログに指定した S3 の `logs/` を見るのが近道です。プライマリノードに SSH でつないでいれば、Spark のログは `/mnt/var/log/spark` にあります（公式チュートリアル）。

### 9.2. 台数とインスタンスタイプでコストが決まる

EMR は動いている間ずっと課金されるので、**台数とインスタンスタイプ、止め忘れ**がコストに直結します。コストを抑えるには、スポットインスタンスや EMR マネージドスケーリング、自動終了を組み合わせます。なお、コアノードは HDFS のデータを持つので、コアノードをスポットにするとデータを失うおそれがあると公式ドキュメントに書かれています。スポットはまずタスクノードで使うのが無難です。
