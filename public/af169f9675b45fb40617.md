2025 年 1 月に書いた記事です。2026 年 10 月に、公式ドキュメントで内容を確かめ直して更新しました。

## 結論

- **AWS のサービスを中心に、サーバーレスで、エラー処理やリトライをきちんと書きたいなら AWS Step Functions** が向いています。料金は実行した分だけ（Standard は状態遷移の数）なので、小さく始めやすいです
- **Python で依存関係の多いデータパイプラインを書きたい、Airflow のプロバイダー（Snowflake など）を使いたいなら Amazon MWAA** が向いています。ただし MWAA は、環境がある間はずっと時間単位で課金されます
- EMR のジョブを動かすだけなら、どちらでもできます。どちらにも EMR 用の連携が公式に用意されています

複数のプロジェクトで、それぞれ Step Functions と MWAA（Amazon Managed Workflows for Apache Airflow）を導入してきました。この記事は、AWS 上でワークフローの基盤を選ぶ立場の人に向けて、その経験と公式ドキュメントをもとに違いをまとめたものです。

## 前提

- 比べているのは [Amazon MWAA](https://docs.aws.amazon.com/mwaa/latest/userguide/what-is-mwaa.html) と [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html) です
- 2026 年 10 月時点で、MWAA は Apache Airflow 2.x と 3.x の複数のバージョンに対応しています（[Apache Airflow versions on Amazon MWAA](https://docs.aws.amazon.com/mwaa/latest/userguide/airflow-versions.html)）
- 長所と短所の一部は、私がプロジェクトで使ったときの感想です。具体的なプロジェクトの内容は書けないので、一般論として書いています。料金を実際に比べた数字はありません

## 比較表

| 観点 | Amazon MWAA | AWS Step Functions |
|---|---|---|
| **ワークフローの書き方** | Python で DAG を書く | Amazon States Language（JSON ベース）で状態機械を書く。コンソールの Workflow Studio で GUI から組み立てたり、AWS CDK でコードから作ったりもできる |
| **学習コスト** | Airflow の概念（DAG、オペレーター、スケジューラー）を覚える必要がある | 状態の種類（Task、Choice、Parallel、Map など）を覚えれば始められる |
| **スケジュール実行** | Airflow のスケジュール（cron、時間間隔、アセットによるスケジュールなど） | Step Functions 自体には持たず、EventBridge Scheduler などから起動する |
| **AWS サービスとの連携** | Amazon プロバイダーのオペレーターで呼ぶ | 最適化された統合と AWS SDK 統合で、多くの AWS サービスの API を直接呼べる |
| **外部サービスとの連携** | Snowflake などのプロバイダーが豊富 | HTTP Task で HTTPS API を呼ぶか、Lambda を挟む |
| **大量の並列処理** | ワーカーの数の範囲で並列に動かす | Distributed Map で、既定で最大 10,000 の子ワークフローを並列に動かせる |
| **1 回の実行の長さ** | DAG の作り次第 | Standard は最大 1 年、Express は最大 5 分 |
| **料金の考え方** | 環境がある間、時間単位で課金（追加のワーカーなども課金） | Standard は状態遷移の数、Express はリクエスト数と実行時間で課金 |

料金は [Amazon MWAA pricing](https://aws.amazon.com/managed-workflows-for-apache-airflow/pricing/) と [AWS Step Functions pricing](https://aws.amazon.com/step-functions/pricing/)、Standard と Express の違いは [Choosing workflow type in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html) で確かめています。

## MWAA の長所と短所

### DAG とは
Airflow では、ワークフローを **DAG（Directed Acyclic Graph、有向非巡回グラフ）** として書きます。DAG は「タスク」と「タスク同士の依存関係」でできています。依存関係には向きがあり（有向）、たどっても元のタスクに戻ってくる輪はできません（非巡回）。

Airflow のドキュメントでは、DAG はワークフローを実行するために必要なもの（スケジュール、タスク、タスクの依存関係など）をまとめたもの、と説明されています（[Dags](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html)）。タスクは、上流のタスクが成功してから実行されるのが基本です。

ここでいうワークフローは、データの取り込み、変換、分析といった一連の処理のことです。私のいる現場では、DAG を便宜的に「ジョブ」と呼ぶことが多いです。

### 長所
- **依存関係の多いワークフローを書きやすい**: 分岐や合流のあるタスクの依存関係を、DAG としてそのまま書ける
- **Python で柔軟に書ける**: DAG もタスクの中身も Python で書ける
- **プロバイダーが多い**: Airflow には AWS、Snowflake などのサービス向けのプロバイダー（オペレーター、フック、センサーの集まり）があり、MWAA でも使える（[Operators and Hooks Reference](https://airflow.apache.org/docs/apache-airflow-providers/operators-and-hooks-ref/index.html)）

### 短所
- **始めるまでが重い**: Airflow の概念と、MWAA の環境づくり（VPC、S3 の DAG フォルダー、requirements.txt など）を覚える必要がある。Python と、JP1 のような既存のジョブスケジューラーの考え方に慣れていないと、一から作るのは大変だと感じました
- **小さな用途には割高になりやすい**: 環境がある間はずっと課金されるので、たまにしか動かさないワークフローだけのために置くと割高になる

## Step Functions の長所と短所

### 長所
- **組み立てやすい**: Workflow Studio で、GUI からワークフローを組み立てられる（[Developing workflows in Step Functions Workflow Studio](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-studio.html)）。定義は Amazon States Language の JSON なので、AWS CDK などでコードとして管理することもできる（[AWS Step Functions Construct Library](https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_stepfunctions-readme.html)）
- **AWS サービスとの連携が強い**: AWS SDK 統合を使うと、200 を超える AWS サービスの API を Lambda なしで呼べる（[Integrating services with Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/integrate-services.html)）
- **サーバーレスで、使った分だけの料金**: 動かしていない間の料金がかからない
- **状態の遷移を宣言的に書ける**: 各処理を「状態（ステート）」として定義し、成功・失敗・リトライ・分岐で次にどこへ進むかを JSON で書く。リトライや失敗時の分岐は `Retry` と `Catch` で書ける（[Handling errors in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)）
- **状態の間のデータの受け渡しを任せられる**: 前の状態の出力が次の状態の入力になり、変数や JSONata で加工もできる（[Transforming data with JSONata in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/transforming-data.html)）。個人的には、これがいちばんありがたいところです。状態の保存を自分で作り込まずに済みます
- **大量の並列処理もできる**: Distributed Map で、S3 の大きな CSV や大量のオブジェクトを、子ワークフローに分けて並列に処理できる（[Using Map state in Distributed mode](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html)）

### 短所
- **依存関係が込み入ると定義が読みにくくなる**: Parallel や Map で並列や合流は書けるが、たくさんのタスクが網の目のように依存し合うワークフローは、JSON の定義が長くなって追いにくい。こういうワークフローは Airflow の DAG の方が素直に書けると感じました
- **スケジュール実行は別のサービスと組み合わせる**: 定期実行は EventBridge Scheduler などから起動する（[Using Amazon EventBridge Scheduler to start a Step Functions state machine execution](https://docs.aws.amazon.com/step-functions/latest/dg/using-eventbridge-scheduler.html)）
- **AWS 以外のサービスは自分でつなぐ**: Snowflake のような外部サービス向けの統合は用意されていないので、Lambda を挟むか、HTTP Task で HTTPS API を呼ぶ

## 図で見る違い

### Step Functions の状態遷移

```
+----------------+       +----------------+       +----------------+
|   タスク A     | ----> |   タスク B     | ----> |   タスク C     |
+----------------+       +----------------+       +----------------+
        |                        |                         |
    失敗時は Retry / Catch で、リトライや別の状態への分岐を決める
```

### MWAA（Airflow）の DAG

```
        +--> [ Task B ] --+
        |                 |
[ Task A ]                +--> [ Task D ]
        |                 |
        +--> [ Task C ] --+
```

Task A が終わると Task B と Task C が並列に動き、両方が終わってから Task D が動きます。矢印は一方向で、Task D から Task A に戻る輪は作れません。

## ユースケース

### MWAA が合う例

1. **データパイプライン（ETL）**
   - S3 に置いたデータを Glue で変換し、Redshift にロードする
   - 依存関係の多い処理を DAG で管理できる
2. **機械学習のワークフロー**
   - S3 でのデータ準備、SageMaker での学習、評価とデプロイ
   - 段階が多いワークフローを、Python で柔軟に組める
3. **定期実行のレポート**
   - 毎日決まった時刻にレポートを作り、S3 に保存して、SNS で通知する
   - スケジュールを DAG と一緒に書ける

### Step Functions が合う例

1. **サーバーレスアプリケーションの処理の流れ**
   - API Gateway でリクエストを受け、Lambda で処理し、DynamoDB に保存する
   - AWS サービスを直接呼べるので、Lambda を減らせることもある
2. **エラー処理つきのバッチ**
   - 外部 API を呼び、失敗したらリトライし、失敗が続いたら SNS で通知する
   - `Retry` と `Catch` で宣言的に書ける
3. **マイクロサービスの連携**
   - EC サイトの注文で、在庫を確認し、在庫があれば決済し、出荷を指示する
   - 処理の流れを状態機械として 1 か所で見られる

## 要件別に比べる

### 1. Amazon EMR で大規模な ETL を動かしたい

#### Amazon MWAA
- **長所**
  - Airflow の Amazon プロバイダーに EMR 用のオペレーターとセンサーがある。クラスターの作成は `EmrCreateJobFlowOperator`、ステップの追加は `EmrAddStepsOperator`、完了待ちは `EmrStepSensor`、終了は `EmrTerminateJobFlowOperator` など（[Amazon EMR（Amazon プロバイダー）](https://airflow.apache.org/docs/apache-airflow-providers-amazon/stable/operators/emr/emr.html)）。以前の版で `EmrCreateClusterOperator` と書いていたのは誤りでした
  - EMR の前後に別の処理（データの取り込み、品質チェック、後続のロードなど）が多い場合に、DAG で依存関係をまとめやすい
  - 複数の ETL ジョブの定期実行や、失敗時のリトライを細かく設定できる
- **短所**
  - クラスターの設定が込み入ってくると、DAG のコードが長くなり保守しにくくなることがある

#### Step Functions
- **長所**
  - EMR とは「最適化された統合」があり、`createCluster.sync`（クラスターが待機中になるまで待つ）、`addStep.sync`（ステップの完了まで待つ）、`terminateCluster.sync` などを使える（[Create and manage Amazon EMR clusters with Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/connect-emr.html)）
  - エラー処理、リトライ、条件分岐を短く書ける
- **短所**
  - 公式ドキュメントにあるとおり、実行を途中で止めても Step Functions は EMR のクラスターを自動では終了しない。終了の処理を失敗時の分岐にも入れておかないと、クラスターが動き続けて課金される
  - EMR の前後の処理が多く、依存関係が網の目になると、定義が長くなりやすい

#### 結論
- **MWAA** は、EMR の前後に処理が多く、依存関係の多い ETL をまとめて管理したい場合に向いています
- **Step Functions** は、「クラスターを作る、ステップを流す、終了する」といった比較的まっすぐな EMR のジョブに向いています

### 2. Lambda や Snowflake と組み合わせたサーバーレスな構成

#### Amazon MWAA
- **長所**
  - Airflow の Snowflake プロバイダーに、`SQLExecuteQueryOperator`（Snowflake 向けの使い方）や `SnowflakeSqlApiOperator`、`CopyFromExternalStageToSnowflakeOperator` などが用意されている（[Snowflake operators](https://airflow.apache.org/docs/apache-airflow-providers-snowflake/stable/operators/index.html)）。自分でオペレーターを作らなくても、クエリの実行やデータのロードを書ける
  - 複雑なタスクの依存関係を DAG で整理でき、全体の流れを UI で見やすい
  - Lambda、S3、RDS などとも連携できる
- **短所**
  - MWAA の環境そのものはサーバーレスではなく、環境がある間は課金される。軽い処理を少し動かすだけだと、コストが見合わないことがある

#### Step Functions
- **長所**
  - サーバーレスで、Lambda と組み合わせやすい
  - Snowflake には Step Functions の専用の統合がないので、Snowflake のコネクターを入れた Lambda でクエリを実行し、その Lambda を Step Functions から呼ぶ形が組みやすいです。HTTPS API を直接呼ぶ HTTP Task もあります（[Call HTTPS APIs in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/call-https-apis.html)）
  - 状態の受け渡しを任せられ、定義をコードで管理できる
- **短所**
  - タスク間の依存関係が込み入ると、JSON の定義が増えて保守しにくくなる

#### 結論
- **Step Functions** は、Lambda、DynamoDB、S3 など AWS のサービスが中心の軽いワークフローに向いています
- **Amazon MWAA** は、Snowflake を含む外部サービスとの連携が多い ETL に向いています

## 選択基準のまとめ

| 要件 | 候補 | 理由 |
|---|---|---|
| 依存関係の多い EMR ベースの ETL | MWAA | DAG でタスクを整理でき、EMR 用のオペレーターとセンサーがそろっている |
| 「作る・流す・終了する」程度の EMR ジョブ | Step Functions | EMR の最適化された統合（`.sync`）で、待ち合わせやリトライを短く書ける |
| サーバーレスの ETL や API の裏側の処理 | Step Functions | Lambda や AWS サービスと直接つながり、使った分だけの料金で済む |
| Snowflake を含む外部サービスとの連携が多い ETL | MWAA | 公式のプロバイダーをそのまま使える |
| S3 上の大量のファイルを並列に処理したい | Step Functions | Distributed Map で大量の子ワークフローを並列に動かせる |
| 定期実行のジョブがたくさんあり、Python で管理したい | MWAA | スケジュールと依存関係を DAG の中に書ける |
| 動かす頻度が低く、コストを抑えたい | Step Functions | MWAA は環境がある間ずっと課金される |

## 確かめていないこと

- 同じワークフローを両方で動かしたときの、実際の料金の差
- HTTP Task から Snowflake の SQL API を呼ぶ構成が、認証方式（EventBridge の接続で扱える Basic、OAuth、API キー）とうまく合うか。Snowflake の SQL API そのものは [Snowflake SQL API](https://docs.snowflake.com/en/developer-guide/sql-api/index) にあります
- Airflow 3.x の MWAA で、この記事の Airflow 2.x 時代の感想がそのまま当てはまるか
