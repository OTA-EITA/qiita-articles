AIエージェントに仕事を任せるとき、「ハーネス」を誰が設計するのか。エンジニアだけで決めると、ビジネス側が決めるべきことが、コードの中で決まってしまうことがあります。

この記事は、ビジネス側の人とエンジニアが、同じ表を見て分担を決めるための整理です。材料は、Anthropic が公開している 2 本のエンジニアリング記事です。

> この記事は、2 本の記事を読んで整理したものです。数字と引用は元記事のもので、自分の環境で動かして確かめた結果ではありません。

## ハーネスとは

この記事では、AIモデルの外側にある、動かす仕組みの全体を指します。どの道具を使わせるか、どこまで任せるか、終わったかをどう判定するか、前回の続きをどう引き継ぐか。モデルそのものではなく、その周りの設計です。

Anthropic の記事には、こう書かれています。

> every component in a harness encodes an assumption about what the model can't do on its own

訳すと「ハーネスのどの部品も、モデルが単独ではできないことについての仮定を符号化している」です。ハーネスは「このAIは、ここまでは一人でできない」という仮定の集まりです。その仮定を置くのが、エンジニアだけでよいのか。これがこの記事の問いです。

## 長く動かすと、同じ失敗が起きる

[長時間動くエージェントのハーネス](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（2025-11-26）は、Claude で観察した失敗を、4 つに分けています。

| 失敗（原文の表） | 何が起きるか |
|---|---|
| 早すぎる完了宣言 | プロジェクト全体を、まだ終わっていないのに「終わった」と判断する |
| 散らかった環境 | バグや、記録されていない進捗を残したまま、回を終える |
| 機能の早すぎる完了マーク | 確かめきれていない機能を、できたことにする |
| 動かし方の調査 | アプリの動かし方を調べるのに、時間を使う |

根にあるのは、この一文です。

> each new session begins with no memory of what came before

新しい回は、前の回を何も覚えていません。だから、覚えさせる仕組みが要ります。

## 元記事の対策には、人が決めることが混じっている

元記事が示す対策を並べます。機能リストの中身と、テストを消さないというルールは、コードの前に、人が決めることです。

- **機能リスト** を作る。200 を超える機能を、すべて `"passes": false` で始める
- **1 回に 1 機能** だけ進める
- 新しい機能に取りかかる前に、**基本のエンドツーエンドのテストを実行** して、壊れていないか確かめる
- 進み具合を、**Git へのコミットと進捗ファイル** に残す
- テストを消したり書き換えたりしない。元記事は「許容できない」と書いています

> It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality

## ビジネスが決めることと、エンジニアが作ること

上の対策に、2 本目の記事の考え方を重ねて、分担を表にします。

| 部品 | ビジネスが決めること | エンジニアが作ること |
|---|---|---|
| 完了の定義 | 何ができたら「完了」か | 機能リストと、自動で動くテスト |
| 採点の基準 | 良い出来と悪い出来の違い、その実例 | 評価する役の実装と、基準による調整 |
| 記録と引き継ぎ | 後から確認できるように、何を残すか | 進捗ログの形式と、履歴の保存 |
| 守らせるルール | 変えてはいけないものは何か | 変更を止める仕組み |
| コスト | 品質にいくらまで払うか | 部品の厚さの調整 |

この表は、Anthropic の記事に書かれた分担ではなく、私の整理です。元記事が書いているのは、右の列に近い、仕組みの側です。

2 本目の記事（[アプリ開発向けのハーネス設計](https://www.anthropic.com/engineering/harness-design-long-running-apps)、2026-03-24）は、作る役（Generator）と評価する役（Evaluator）を分けています。自分の仕事を採点させると、出来が平凡でも自信を持って褒めがちだからです。

ただし、分けただけでは甘さは消えません。原文は、評価役も LLM であり、LLM が作ったものに寛容になりやすいと書いています。そこで元記事の筆者は、採点の内訳をつけた具体例を見せて、評価役を調整しました。

**良し悪しの基準と、その具体例を出すのは人**、という点が、ビジネス側の仕事です。

## 例：経費申請をチェックするエージェント

説明のための例です。実在する会社の事例ではありません。

ビジネス側が書くのは、次のような文です。

- 領収書がない申請は、差し戻す
- 上限額を超えたら、上長の承認に回す
- 勘定科目が決まっていないものは、確定させない

エンジニアは、これを機能リストにします。元記事の `passes` の形に合わせた、簡略版の例です。

```json
[
  { "id": "receipt-required", "description": "領収書がない申請は差し戻す", "passes": false },
  { "id": "limit-approval", "description": "上限額を超えたら上長の承認に回す", "passes": false },
  { "id": "account-unset", "description": "勘定科目が未定のものは確定させない", "passes": false }
]
```

全部が `false` で始まり、確かめられたものだけを `true` にします。「終わった」と言えるのは、全部が `true` になったときだけです。この **完了の定義** を、ビジネス側の言葉で書けるかどうかが、分かれ目です。

## ハーネスの厚さは、コストになる

2 本目の記事に、構成ごとの時間と費用があります。ゲーム制作は、同じプロンプトを 2 通りの構成で動かした数字です。

| 課題と構成 | 時間 | 費用 | 結果（原文の記述） |
|---|---|---|---|
| ゲーム制作、単独実行（solo） | 20分 | $9 | 画面にはものが出るが、操作に反応せず、ゲームとして壊れていた |
| ゲーム制作、フルハーネス | 6時間 | $200 | 操作して遊べた。物理には粗さが残る |
| 音楽制作ソフト（DAW）、モデル更新後のハーネス | 3時間50分 | $124.70 | （この表では結果は比べていません） |

この数字は、Anthropic の実験のものです。自分の業務では、違う数字になります。

この例で読めるのは、**20 倍以上の費用で、動かないものが動くものになった** ということです。厚くするほど時間と費用がかかり、そのぶん、結果が変わりました。

どこまで厚くするかは、品質にいくら払うかの問題です。エンジニアだけで決めることではありません。

## 部品は、外していく

最初の仮定の話に戻ります。ハーネスの部品は「モデルができないこと」の仮定なので、モデルが良くなったら、外せるものが出てきます。

元記事は、モデルの更新後に、作業を区切る単位（スプリント）をやめ、評価を最後の 1 回にまとめました。評価役は、課題が今のモデルが単独で確実にできる範囲を超えるときに、費用に見合うと書いています。

作った部品を、置きっぱなしにしない。ビジネス側とエンジニアが、定期的に見直す約束も、ハーネスの設計に入ります。

## 今日からできること

1. 任せたい仕事を 1 つ選び、**「完了」の条件を 3 つ、業務の言葉で** 書く
2. その条件を、エンジニアと一緒に **自動で確かめられる形** にする
3. 「何を残すか」を決める。後から人が見て、判断を追えるようにする
