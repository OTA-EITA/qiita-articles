AIエージェントに仕事を任せるとき、「ハーネス」を誰が設計するのか。エンジニアだけで決めると、ビジネス側が決めるべきことが、いつの間にかコードの中で決まります。

この記事は、ビジネス側の人とエンジニアが、同じ表を見て分担を決めるための整理です。材料は、Anthropic が公開している 2 本のエンジニアリング記事です。

> この記事は、2 本の記事を読んで整理したものです。数字と引用は元記事のもので、自分の環境で動かして確かめた結果ではありません。

## ハーネスとは

AIモデルの外側にある、動かす仕組みの全体です。どの道具を使わせるか、どこまで任せるか、終わったかをどう判定するか、前回の続きをどう引き継ぐか。モデルそのものではなく、その周りの設計を指します。

Anthropic の記事には、こう書かれています。

> ハーネスの各部品は、モデルができないことについての仮定を符号化する

つまりハーネスは「このAIは、ここまではできない」という仮定の集まりです。その仮定を置くのが、エンジニアだけでよいかというのが、この記事の問いです。

## 長く動かすと、同じ失敗が起きる

[長時間動くエージェントのハーネス](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（2025-11-26）は、失敗を 4 つに分けています。

| 失敗 | 何が起きるか |
|---|---|
| 一度に全部やろうとする | 全機能を一気に作ろうとして、途中で力尽きる |
| 早すぎる完了宣言 | 進み具合を見て、未完成のまま「終わった」と判断する |
| テスト不足 | 実際の操作で確かめずに、できたことにする |
| 散らかった引き継ぎ | 次の回が、壊れた状態から始まる |

根にあるのは、この一文です。

> each new session begins with no memory of what came before

新しい回は、前の回を何も覚えていません。だから、覚えさせる仕組みが要ります。

## 元記事の対策は、ほとんどが「決めごと」

元記事が示す対策を並べると、コードの前に、人が決めることが多いと分かります。

- **機能リスト** を作る。200 を超える機能を、すべて `passing: false` で始める
- **1 回に 1 機能** だけ進める
- 回の最初に **テストを実行** して、壊れていないか確かめる
- **進捗ファイルとGitの履歴** に、やったことを残す
- テストを消したり書き換えたりしない。元記事は「許されない」と書いています

> It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality

## ビジネスが決めることと、エンジニアが作ること

ここからが、この記事の本題です。上の対策に、2 本目の記事の考え方を重ねて、分担を表にします。

| 部品 | ビジネスが決めること | エンジニアが作ること |
|---|---|---|
| 完了の定義 | 何ができたら「完了」か | 機能リストと、自動で動くテスト |
| 採点の基準 | 良い出来と悪い出来の違い、その実例 | 評価する役の実装と、基準による調整 |
| 記録と引き継ぎ | 後から確認できるように、何を残すか | 進捗ログの形式と、履歴の保存 |
| 守らせるルール | 変えてはいけないものは何か | 変更を止める仕組み |
| コスト | 品質にいくらまで払うか | 部品の厚さの調整 |

2 本目の記事（[アプリ開発向けのハーネス設計](https://www.anthropic.com/engineering/harness-design-long-running-apps)、2026-03-24）は、作る役と評価する役を分けています。自分の仕事を採点させると、甘くなるからです。評価の基準は、人の好みを具体的な採点項目にして、評価役に覚えさせています。

**良し悪しの基準を決めるのは人**、という点が、ビジネス側の仕事です。

## 例：経費申請をチェックするエージェント

説明のための例です。実在する会社の事例ではありません。

ビジネス側が書くのは、次のような文です。

- 領収書がない申請は、差し戻す
- 上限額を超えたら、上長の承認に回す
- 勘定科目が決まっていないものは、確定させない

エンジニアは、これを機能リストにします。元記事の形に合わせると、こうなります。

```json
[
  { "id": "receipt-required", "description": "領収書がない申請は差し戻す", "passing": false },
  { "id": "limit-approval", "description": "上限額を超えたら上長の承認に回す", "passing": false },
  { "id": "account-unset", "description": "勘定科目が未定のものは確定させない", "passing": false }
]
```

全部が `false` で始まり、テストが通ったものだけを `true` にします。「終わった」と言えるのは、全部が `true` になったときだけです。この **完了の定義** を、ビジネス側の言葉で書けるかどうかが、分かれ目です。

## ハーネスの厚さは、コストになる

2 本目の記事に、同じ課題を別の構成で動かした数字があります。

| 課題と構成 | 時間 | 費用 |
|---|---|---|
| ゲーム制作、ハーネスなし（単独） | 20分 | $9 |
| ゲーム制作、フルハーネス | 6時間 | $200 |
| 音楽制作ソフト、更新後のハーネス | 3時間50分 | $124.70 |

この数字は、Anthropic の実験のものです。自分の業務では、違う数字になります。ただ、**厚くするほど時間と費用がかかる** という向きは変わりません。

どこまで厚くするかは、技術の問題ではなく、品質にいくら払うかの問題です。エンジニアが決めることではありません。

## 部品は、外していく

最初の仮定の話に戻ります。ハーネスの部品は「モデルができないこと」の仮定なので、モデルが良くなったら、外せるものが出てきます。

元記事は、モデルの更新後に、細かく区切る進め方をやめ、評価を 1 回にまとめました。評価役を動かすのは、課題が今のモデルの確実にできる範囲を超えるときだけにしています。

作った部品を、置きっぱなしにしない。ビジネス側とエンジニアが、定期的に見直す約束も、ハーネスの設計に入ります。

## 今日からできること

1. 任せたい仕事を 1 つ選び、**「完了」の条件を 3 つ、業務の言葉で** 書く
2. その条件を、エンジニアと一緒に **自動で確かめられる形** にする
3. 「何を残すか」を決める。後から人が見て、判断を追えるようにする
